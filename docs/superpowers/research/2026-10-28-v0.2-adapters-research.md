## 0. Najważniejsze ustalenia

1. **Letta: format `.af` jest wycofany.** README `letta-ai/letta-code` mówi wprost, że eksport i import AgentFile zostały usunięte z Letta Code (`/export`, `/download`, `--import`, `--from-af`) [L5]. Stary serwer V1 jest zarchiwizowany [L4]. Dokumentacja REST Letta Cloud nadal opisuje `GET /v1/agents/{id}/export` i `POST /v1/agents/import`, ale z oznaczeniami „deprecated" przy większości parametrów [L7][L8]. Dziś „agent Lettego" to agent Letta Code: stan w repozytorium git (MemFS), harmonogramy w `~/.letta/crons.json` lub w chmurze. Adapter powinien celować w MemFS, a `.af` traktować jako opcjonalną ścieżkę legacy.
2. **Codex: katalog skilli użytkownika to `~/.agents/skills`, nie `~/.codex/skills`.** Kod Codexa nadal czyta `$CODEX_HOME/skills`, ale komentarz w kodzie nazywa to „deprecated user skills location" [C10]. Oficjalna dokumentacja podaje `$HOME/.agents/skills` [C1]. Importer Hermesa wciąż czyta `~/.codex/skills` [H1] — to starsza konwencja.
3. **Grok Bot nie ma natywnego eksportu, CLI ani API.** To produkt chmurowy (komputer w chmurze hostowany przez Cursor); dokumentacja o eksporcie milczy [G2][G4][G6]. Jedyna działająca ścieżka wyjścia to skill uruchamiany przez samego Bota, który pakuje agentów do zipa `openbot-agent-import` v1 [G12]. Adapter `grok-bot` = czytanie takiego zipa + „handoff" przy zapisie.
4. **Hermes ma najczystszy model do adaptera plikowego.** Profil to katalog, a odczyt i zapis nie wymagają demona. Pułapki: twarde limity pamięci (2200 i 1375 znaków), jedna globalna strefa czasowa dla wszystkich zadań cron oraz skanery bezpieczeństwa, które mogą odrzucić zapisywaną treść.
5. **Team API OpenBota nie nadaje się jako powierzchnia headless na desktopie** (rozdział 5).

## 1. Hermes Agent (Nous Research)

### 1.1 Gdzie żyją agenci, czy „agent" jest obiektem pierwszej klasy

- Katalog domowy: `~/.hermes` (Linux/macOS) oraz `%LOCALAPPDATA%\hermes` na Windows (fallback `~\AppData\Local\hermes`) [H16]. Nadpisania: `HERMES_HOME`, `HERMES_DATA_DIR_SUFFIX` [H16]. Dokumentacja pokazuje tylko `~/.hermes` [H3], więc ścieżka Windows pochodzi z kodu.
- **Jednostką jest profil, nie „agent".** Profil domyślny to sam `~/.hermes`; profile nazwane leżą w `~/.hermes/profiles/<name>/` [H4]. Katalog jest profilem, jeśli zawiera jeden z plików: `config.yaml`, `.env`, `SOUL.md`, `profile.yaml`, `auth.json`, `state.db` [H4] (to samo robi czytnik OpenBota [H20]). Profil staje się „botem" (Bot Mode) dopiero, gdy jego `profile.yaml` ma blok `ui_meta: hermes-bots` [H10]. Dokumentacja odpowiada „Not exactly" na pytanie, czy profil to pierwszoklasowy agent [H4].
- `HERMES_HOME` jest granicą profilu: config, `.env`, pamięć, sesje, skille, logi, cron i stan gatewaya rozwiązują się względem niego [H4]. Dokumentacja: „Never point two agent processes at the same profile" [H4] — adapter zapisujący do profilu z działającym gatewayem powinien to wykryć lub ostrzec [ZAŁ: mechanizm wykrycia, np. PID lub `pgrep`, nie był sprawdzany].
- Nazwa wyświetlana domyślnego profilu: `display_name` w `~/.hermes/profile.yaml` [H4]. Opis: `hermes profile create <name> --description "<role>"` [H4]. Awatar: dokumentacja Bot Mode mówi, że wygląd, tytuł i opis leżą w metadanych profilu na backendzie, ale nie podaje nazw pól [H10]. Wniosek: **brak udokumentowanego pola awatara w plikach**, `capabilities.avatar = false`.

### 1.3 Zadania cykliczne (cron)

- Plik: `<HERMES_HOME>/cron/jobs.json` (per profil — kod mówi o tym wprost [H13]). Format zapisu: `{"jobs": [...], "updated_at": "..."}`; odczyt toleruje też goły zapis tablicowy [H13][H20]. Wyniki: `cron/output/{job_id}/{timestamp}.md`; dziennik wykonań: `cron/executions.db` (SQLite) [H7]. Dokumentacja odradza ręczną edycję `jobs.json`, zaleca `hermes cron edit` lub `/cron` [H7].
- Pola zadania z `create_job` (kod): `id` (12 znaków hex), `name`, `prompt`, `skills[]`, `skill`, `model`, `provider`, `base_url`, `script`, `no_agent`, `schedule`, `schedule_display`, `repeat {times, completed}`, `enabled`, `state` (`scheduled|paused|completed|running`), `paused_at`, `paused_reason`, `created_at`, `next_run_at`, `last_run_at`, `last_status`, `deliver`, `origin`, `enabled_toolsets`, `workdir`, oraz opcjonalne `reasoning_effort`, `failure_deliver`, `interpreter`, `attach_to_session` [H13].
- **Typy harmonogramu** (`schedule.kind`): `cron {expr, display}`, `interval {minutes, display}`, `once {run_at, display}` [H13]. Parser przyjmuje: `30m`, `every 2h`, `in 30m`, `0 9 * * *`, timestamp ISO; frazy typu `every monday 9am` wymagają pakietu `croniter` [H7][H13].
- **Strefa czasowa jest globalna**, nie per zadanie: kolejność `HERMES_TIMEZONE` → klucz `timezone` w `config.yaml` → czas lokalny serwera [H15]. Naiwny timestamp jest interpretowany w skonfigurowanej strefie Hermesa [H13]. To główna stratność dla `Routine.timezone`.
- CLI: `hermes cron create "<schedule>" "<prompt>" [--name] [--skill]... [--deliver] [--paused] [--paused-reason] [--workdir] [--model] [--provider] [--reasoning-effort] ...`, `list`, `edit`, `pause|resume|run|remove`, `status`, `tick`, `runs`, `doctor` [H7][H9]. **Dokumentacja nie podaje flagi `--json` dla `cron list`** [H9]. `--paused` odpowiada naszemu „routines arrive disabled".
- Gateway: zadania agentowe odpalają się tylko, gdy działa demon gateway (tick co 60 s); `hermes cron tick` bez gatewaya pomija zadania agentowe [H7][H8]. Samo zapisanie lub odczytanie `jobs.json` demona nie wymaga.
- Mapowanie harmonogramów: `cron`→`cron`; `every`→`interval` (m/h/d przeliczone na minuty); `at`→`once` (zadanie z datą w przeszłości jest odrzucane przy tworzeniu [H13], więc trzeba je pominąć z ostrzeżeniem). Prompt cron jest skanowany pod kątem prompt injection i eksfiltracji poświadczeń przy tworzeniu i aktualizacji [H7] — zapis może zostać odrzucony.

### 1.4 Pamięć

- Pliki: `memories/MEMORY.md` (notatki agenta) i `memories/USER.md` (profil użytkownika) [H5]. **Format na dysku**: wpisy rozdzielone sekwencją `"\n§\n"` (stała `ENTRY_DELIMITER`), wpisy mogą być wieloliniowe [H14] (potwierdza czytnik OpenBota [H20]). Plik czytany jako UTF-8 z obsługą BOM [H14].
- **Limity**: `memory_char_limit: 2200` i `user_char_limit: 1375` w sekcji `memory:` pliku `config.yaml`; zapis ponad limit kończy się błędem narzędzia `memory`, nie obcięciem; pamięć nie jest automatycznie kompaktowana [H3][H5]. `write_approval` (domyślnie `false`) może wymusić zatwierdzanie zapisów [H3].
- Nie ma rozróżnienia „fakty vs proza": wszystko to wpisy tekstowe. Zewnętrzni dostawcy pamięci (Honcho, Mem0, Hindsight itd.) działają obok plików; historia sesji siedzi w `state.db` (SQLite, FTS5) [H5].
- Wpisy pamięci są skanowane funkcją `_scan_memory_content` (zakres „strict"): trafiają do promptu systemowego, więc treść wyglądająca na wstrzyknięcie zostanie odrzucona [H14].
- Importery Hermesa pokazują jego własne rozumienie: `CLAUDE.md`, `AGENTS.md` (Codex, Cursor), reguły Cursora i `memories/*.md` Codexa **wszystkie wpadają jako wpisy do `memories/MEMORY.md`**, z deduplikacją i kopią `MEMORY.md.bak.<timestamp>` [H1][H2]. Instrukcje bywają więc traktowane jak pamięć — to nie jest model, który chcemy kopiować.

### 1.5 Eksport/import i CLI

- `hermes profile export <name>` → `<name>.tar.gz` (skille, pamięć, `SOUL.md`, cron, pluginy, ustawienia; klucze API usuwane; bez `installs/`, `tools/`, `cache/`); `hermes profile import ./x.tar.gz --name n` [H4]. Wewnętrzny układ archiwum nie jest opisany [ZAŁ: odzwierciedla katalog profilu].
- **Dystrybucje profili** (format do dzielenia się): katalog z `distribution.yaml`, w którym wymagane jest tylko `name`; opcjonalne `version`, `description`, `hermes_requires`, `author`, `license`, `env_requires[] {name, description, required, default}`, `distribution_owned[]`, `source` [H12][H17]. Zawartość: `SOUL.md`, `config.yaml`, `mcp.json`, `skills/`, `cron/jobs.json` (nowe zadania instalują się wstrzymane), `README.md`. **Pamięć, sesje, `auth.json`, `.env` są zawsze wykluczone** [H12]. Instalacja: `hermes profile install <źródło> --alias`, `hermes profile update <name>`, `hermes profile info <name>` [H12].
- `hermes import-agent [openclaw|claude-code|codex|cursor]` (plugin `agent-importers` v1.1.0, wymaga Hermes >= 0.21.6): `--dry-run`, `--source <path>`, `--overwrite`, `--yes`, `--sync`; zawsze pokazuje plan przed zapisem, bez TTY zatrzymuje się po podglądzie, o ile nie podano `--yes` [H1][H19]. **Brak flagi JSON i brak zdefiniowanego formatu raportu** [H2]. - Inne komendy headless: `hermes -z "<prompt>"` (sam wynik), `hermes chat -q ... --format stream-json`, `hermes config get <klucz> --json`, `hermes usage --json`, `hermes backup`, `hermes import <zip>` [H9]. `--json` istnieje tylko dla wybranych komend; **nie udokumentowano go dla `skills list`, `cron list`, `profile list`** [H9] — adapter powinien czytać pliki, nie parsować wyjścia CLI.

### 1.6 Limity i miejsca stratne

- Pamięć: 2200 + 1375 znaków (konfigurowalne w `config.yaml`) — fakty ponad limit trzeba zagregować, zaproponować podniesienie limitu albo przenieść do notatki w skillu [ZAŁ: który wariant wybrać].
- Strefa czasowa cron jest globalna — `Routine.timezone` różne od strefy profilu daje przybliżenie (zachować w `x-hermes`) i ostrzeżenie.
- `instructions` vs `persona`: brak osobnego miejsca; ryzyko sklejenia w `SOUL.md`.
- `deliver`, `repeat`, `workdir`, `enabled_toolsets`, `skills[]` w zadaniu cron nie mają odpowiedników w `Routine` — zachować w `x-hermes`.
- Skanery bezpieczeństwa (pamięć, prompty cron, skille: wbudowany skaner z werdyktem `dangerous`) mogą odrzucić zapis; adapter musi umieć zgłosić „skipped" z powodem [H5][H6][H7][H14].
- `SKILL.md`: brak twardego limitu; ostrzeżenie lintera powyżej ok. 24 tys. znaków treści i powyżej 60 plików referencji [H6].

## 2. Codex (OpenAI Codex CLI i aplikacja)

Uwaga o źródłach: adresy `developers.openai.com/codex/...` przekierowują (308) na `learn.chatgpt.com/docs/...`; poniżej podano adresy docelowe. Strona CLI reference była za długa i odczytałem tylko jej pierwsze 100 tys. znaków [C6].

### 2.1 Gdzie żyją agenci, czy „agent" jest obiektem pierwszej klasy

- `CODEX_HOME`, domyślnie `~/.codex` [C2][C5]; na Windows ślady w zgłoszeniu błędu wskazują `%USERPROFILE%\.codex` [C12]. W `CODEX_HOME`: `config.toml`, `auth.json` (tylko przy magazynie plikowym), `history.jsonl` (opcjonalnie), logi i cache [C5].
- Warstwy konfiguracji: użytkownik `~/.codex/config.toml`, projekt `.codex/config.toml` (tylko dla zaufanych projektów), system `/etc/codex/config.toml`. Kolejność pierwszeństwa: flagi CLI i `-c` > projekt > plik profilu > użytkownik > konfiguracja zarządzana z chmury > system > wartości domyślne [C3].
- **Profile** to osobne pliki `~/.codex/<nazwa>.config.toml` wybierane `--profile <nazwa>` (nazwa: litery, cyfry, myślniki, podkreślenia). Od Codex 0.134.0 tabela `[profiles.<nazwa>]` w `config.toml` i klucz `profile = "..."` nie są już czytane [C5][C3].
- **Własne agenty (subagenci)**: pliki TOML w `~/.codex/agents/` (osobiste) i `.codex/agents/` (projektowe). Wymagane `name`, `description`, `developer_instructions`; opcjonalne `model`, `model_reasoning_effort`, `model_reasoning_summary`, `model_verbosity`, `features.*`, `skills.config`, `skills.bundled.enabled`, `skills.include_instructions`; `sandbox_mode` i `mcp_servers` w pliku agenta nie nadpisują sesji nadrzędnej [C7]. Kod parsera (`deny_unknown_fields`) dopuszcza `name`, `description`, `nickname_candidates` (tylko ASCII: litery, cyfry, spacja, `-`, `_`; bez duplikatów) oraz resztę jako spłaszczony `ConfigToml` [C11]. `agents.enabled` domyślnie `true` [C4].
- **Wniosek**: Codex nie ma nazwanego agenta najwyższego poziomu. „Agent" to złożenie: globalny `AGENTS.md` + `config.toml` (+ plik profilu) + skille + opcjonalnie pliki `agents/*.toml`. Najbliższy obiekt to plik `agents/<nazwa>.toml` albo profil. Propozycja [ZAŁ]: `list` zwraca `default` (globalny `~/.codex`) oraz każdy plik z `~/.codex/agents/*.toml`.

### 2.3 Zaplanowane automatyzacje

- Oficjalnie: zadania cykliczne w aplikacji desktopowej (dziś ChatGPT desktop): prompt, harmonogram (kontrolki lub reguła RRULE wg RFC 5545), model i poziom rozumowania, projekt/worktree (lokalnie lub nowy worktree), tryb sandboxa. Lokalne zadania wymagają włączonej aplikacji i komputera; brak podanych limitów liczbowych [C8]. **Dokumentacja nie podaje miejsca zapisu ani CLI** [C8][C6].
- Nieoficjalnie (zgłoszenie błędu z przykładem pliku): `~/.codex/automations/.../automation.toml` z polami `version`, `id`, `kind = "cron"`, `name`, `prompt`, `status` (np. `"PAUSED"`), `rrule` (np. `RRULE:FREQ=DAILY;BYHOUR=13;BYMINUTE=34;BYSECOND=0;COUNT=1`), `model`, `reasoning_effort`, `execution_environment = "local"`, `target = { type = "projectless" }`, `cwds = ["~"]` [C12]. W tym samym zgłoszeniu pojawia się `DTSTART;TZID=Europe/Zagreb:...` jako sposób zapisu strefy [C12]. Układ podkatalogów per `id`, plik `memory.md` obok oraz baza `~/.codex/sqlite/codex-dev.db` jako ewentualne źródło prawdy pochodzą ze źródeł trzecich i są ze sobą sprzeczne [S3][C14]. Zgłoszenia na GitHubie opisują automatyzacje, które istnieją na dysku, a nie pokazują się w UI [S3: openai/codex#26641, #46789].
- Wniosek: odczyt możliwy z niską pewnością, zapis niewiarygodny. `Schedule.kind = "cron"` dałoby się przełożyć na prosty RRULE (dzienny/tygodniowy), reszta jest przybliżeniem.

### 2.4 Pamięć

- Domyślnie wyłączona; włącza się `[features] memories = true` lub przełącznikiem w aplikacji. Klucze: `memories.generate_memories`, `memories.use_memories`, `memories.disable_on_external_context`, `memories.extract_model`, `memories.consolidation_model`, `memories.max_rollout_age_days` (30), `memories.max_rollouts_per_startup` (16), `memories.max_raw_memories_for_consolidation` (256), `memories.max_unused_days` (30), `memories.min_rollout_idle_hours` (6), `memories.min_rate_limit_remaining_percent` (25) [C4][C9].
- Pliki w `~/.codex/memories/` to „generated state": dokumentacja pozwala je oglądać, odradza ręczną edycję i nie opisuje importu; ustawienia są per maszyna, nie per projekt [C9]. Nazwy plików (`MEMORY.md`, `memory_summary.md`, `raw_memories.md`, `rollout_summaries/`, `skills/`, `memories_extensions/`) pochodzą ze źródła trzeciego [S3][C13].
- Skutek dla adaptera: `read` może wczytać `MEMORY.md` jako jedną notatkę (przybliżenie); `write` nie powinien pisać do `memories/`. Fakty trzeba wpisać do sekcji `AGENTS.md` (przybliżenie).

### 2.5 Eksport/import i CLI

- Brak oficjalnego eksportu/importu agentów. Jest system pluginów: `codex plugin add|list|remove|marketplace ... --json` [C6] (nie badany pod kątem pakowania skilli). Hermes czyta Codexa przez `import-agent` (mapowanie w 1.5) [H1].
- Headless: `codex exec "<prompt>"` z `--json` (JSONL), `-o/--output-last-message`, `--output-schema`, `-p/--profile`, `-C/--cd`, `--skip-git-repo-check`, `--ephemeral`, `--ignore-user-config`, `--ignore-rules`, `--sandbox`; `codex mcp list|get --json`, `add|remove`; `codex features list|enable|disable`; `codex login status`; `codex doctor --json`; `codex cloud list --json`; `codex app-server --listen stdio://|ws://|unix://` (eksperymentalne) [C6]. **Brak podkomend dla skilli, agentów, pamięci i automatyzacji** w odczytanej części [C6].
- Demon: do odczytu i zapisu plików niepotrzebny. Aplikacja desktopowa musi działać, aby lokalne automatyzacje się odpalały [C8]. Do testów `CODEX_HOME` można wskazać na katalog tymczasowy (wzorzec z dokumentacji: `CODEX_HOME=$(pwd)/.codex codex exec ...`) [C2].

### 2.6 Limity i miejsca stratne

- `persona` i `instructions` zlewają się w jedno; trzeba je podzielić nagłówkami lub zapisać w `developer_instructions`.
- `AGENTS.md`: 32 KiB łącznie [C2]; lista skilli w prompcie: do 2% okna kontekstu lub 8000 znaków, `skills.max_context_tokens` do 10 000 tokenów [C1] — przy wielu skillach opisy są przycinane.

- Zapis do `~/.agents/skills` jest współdzielony z innymi narzędziami (Grok Build czyta ten katalog [G10]) — efekt uboczny, który adapter powinien zgłaszać.

## 3. Grok Bot (xAI)

### 3.1 Czym jest „agent", gdzie leży

- „Bot" to obiekt pierwszej klasy konta: imię, etykieta/tytuł, awatar. Zadanie definiuje się rozmową [G2]. **Wszystkie Boty konta współdzielą jeden trwały komputer w chmurze** (przeglądarka, system plików, terminal; wspólny `/workspace`; wspólne sesje przeglądarki i logowania), hostowany przez Cursor w USA; praca trwa przy zamkniętym laptopie [G1][G5][G13].
- **Brak pola instrukcji dla osobistych Botów**: „Personal Bots no longer have a description or a Bot settings page"; trwałe zasady Bot trzyma w pamięci [G2]. Boty współdzielone mają opis „About" [G2]. Nieoficjalne CLI `gbot` nazywa pole `description` „the UI Instructions field" [S3][G14] — sprzeczność, być może stan sprzed zmiany [ZAŁ].
- Grupy: czaty 2–6 Botów, wiadomości Bot→Bot [G1][G13]; kod `gbot` egzekwuje maks. 6 członków [S3][G16].
- Lokalnie: aplikacja Electron trzyma w `~/Library/Application Support/Grok Bot`, `%APPDATA%\Grok Bot`, `~/.config/Grok Bot` zaszyfrowaną sesję i poświadczenia routingu, nie listę agentów [S3][G14]. Komunikat błędu w kodzie `gbot`: „The macOS app keeps the live roster on its cloud computer (agent-data/agents), not in ~/Library/Application Support/Grok Bot" [S3][G16]. **Nie ma lokalnego magazynu agentów do odczytu.**
- Na komputerze w chmurze (widocznym z poziomu Bota), wg kodu społeczności: `/home/box/agent-data/agents/<uuid>/` z `profile.json` (`name`, `description`, `title`, `avatarShape`, `avatarColor`), `settings.json` (`notifyOnAgentUpdates`, `hiddenFromSidebar`), `group.json` (`version: 1`, `memberIds`) oraz katalogami `memory/` i `automations/` (format zawartości nieznany) [S3][G16]. Niska–średnia pewność.
- Awatar: w UI wygenerowany lub wgrany obraz do 25 MB [G2]; w API społeczności kształt (18 wartości, m.in. `blob`, `pebble`, `hex`, `leaf`) i kolor (11 wartości) [S3][G16].

### 3.3 Eksport i import

- **Natywnego eksportu nie ma**: strona o Botach „doesn't describe exporting" [G2]; Security: brak masowego eksportu [G6]; FAQ: brak eksportu, API i CLI [G4]. Szablony (Share → Create a copy → Publish → Copy link; odbiorca: Connect apps → Bot templates → Import Bot) niosą tożsamość, opis, skille i rutyny, ale nie pamięć ani historię [G2]. Publiczne strony udostępnienia pokazują tylko pola marketingowe [S3][G18].
- **De facto eksport = skill `openbot-export` uruchamiany przez Bota**: listuje agentów (z pominięciem Bota eksportującego), pyta o pliki, z czatów pisze do 50 faktów na agenta (do 500 znaków każdy), usuwa sekrety, buduje zip w `~/Downloads/openbot-export-<data>.zip` [G12]. README OpenBota wskazuje agenta eksportującego pod `x.ai/bot/gI0XdhhDYPJeyQaqQBC0O` [G19] (sama strona `x.ai/bot` zwróciła 403). Wynik jest niedeterministyczny (robi go LLM).
- **Format zipa `openbot-agent-import` v1** [G12] — korzeń `openbot-import.json`:
  - `format: "openbot-agent-import"`, `version: 1`, `source: {app: "grok-bot", exportedAt}`.
  - `agents[]`: `key` (≤64, `[a-z0-9-]`), `name` (≤80), `title` (≤120), `description` (≤2000; dłuższe → pełny tekst w `agents/<key>/files/INSTRUCTIONS.md`), `avatar` (ścieżka PNG/JPEG/WebP ≤512 KB lub `null`), `skills[]` (≤32 folderów `agents/<key>/skills/<skill>`; folder ≤10 MB i ≤200 plików, `SKILL.md` z frontmatterem), `routines[]` (≤64: `name` ≤80, `instruction`, `active`, `timezone` IANA, `schedule`), `memories[]` (≤64 po ≤500 znaków), `files` (folder lub `null`).
  - `channels[]` (opcjonalne, ≤100): `key`, `name`, `title`, `instructions` (≤2000), `members[]`, `lead`, `routines`, `memories` (≤32).
  - Harmonogramy: `hourly{minute}`, `daily{time}`, `weekdays{time}`, `weekly{weekday 0–6,time}`, `monthly{day,time}`, `interval{amount,unit: minutes|hours|days}`, `custom{expression}`; minimum 3 minuty.
  - Archiwum ≤500 MB i ≤5000 plików; odrzucane: pliki `.env*`, `*private*key*`, zagnieżdżone archiwa, `.git`, `node_modules`.
- Społecznościowy `grok-to-hermes` oczekuje JSON `{profile{name,description?,title?}, memory[{content,kind:"log"|"profile",createdAt?}], skills[{name,description?,content}], routines[{slug?,name,description?,content,schedule?}], plugins[{pluginId,name,description?}]}`, ale to **schemat wymyślony przez autora narzędzia**; README przyznaje, że nie zna źródła takiego eksportu [S3][G18]. Nie opierać się na nim.

Format MemFS: wersja v2 jest wykrywana po istnieniu głównego `MEMORY.md`; pliki `.md` w korzeniu to pamięć rdzeniowa ładowana co turę; podkatalogi z własnym `MEMORY.md` są „rzutowane" (poza kontekstem do czasu użycia); `skills/` nie jest rzutowane; starsza wersja v1 używa katalogu `system/` [L10][L18]. Każda edycja jest commitowana do repozytorium git MemFS; agenty Cloud pushują do repozytorium hostowanego, lokalne commitują lokalnie [L10].

### 4.3 Zadania cykliczne

- CLI: `letta cron add --name <n> --description <t> --prompt <t> (--cron "<wyr>" | --every <interwał> | --at <czas>) [--agent <id>] [--conversation default|<id>|self|new] [--computer <deviceId>]`, `list`, `get`, `runs`, `delete` [L9][L12].

Dobre dopasowanie do `Routine` (`cron`/`at`, `timezone`).
- Harmonogramy tworzone z piaskownicy Cloud są przechowywane w chmurze i wyzwalane zegarem po stronie serwera; cykliczne `--cron` w chmurze liczone w UTC. Lokalne działają tylko, gdy otwarty jest proces CLI lub serwera [L12]. `--every` w pliku lokalnym nie ma osobnego pola — prawdopodobnie zamieniane na cron [ZAŁ].

SDK: `client.agents.export_file(agent_id=...)` i `client.agents.import_file(file=...)` [L1][L6].

### 4.6 Limity i miejsca stratne

- `.af`: brak pasaży archiwalnych; sekrety `null`; **historia wiadomości trafia do pliku** (prywatność — używać `scrub_messages`/`strip_messages`); narzędzia z kodem źródłowym (nigdy nie importować z niezaufanego pliku, nie ustawiać `override_existing_tools`); `llm_config` zależny od dostawcy (mapować tylko uchwyt modelu); `tool_rules`, `groups`/sleeptime, `identity_ids`, pola szablonów i projektu → `x-letta`; bloki współdzielone między agentami trzeba spłaszczyć.
- MemFS: limit repozytorium 5 MiB (plan Free) lub 50 MiB (Pro), liczony wg najnowszego snapshotu, nie historii [L11]; limity per plik istnieją w kodzie (liczone razem z frontmatterem), wartości nie czytałem [S3: memory-constraints.ts]; historia git nie przenosi się poza repozytorium.
- Cron: strefa cykliczna w chmurze to UTC [L12]; w pliku lokalnym `timezone` jest per zadanie [L17].
- Prompt systemowy na Cloud bywa zarządzany przez serwer [L5].

## 5. OpenBot: czy lokalne Team API (`/v1/agent-import/*`) jest dostępne headless na desktopie

Odpowiedź: **w praktyce nie, nie jako wspierana powierzchnia integracji.**

1. `TeamApiServer` to serwer `node:http`, wiązany przez `listenLoopback` do **`127.0.0.1` na wolnym porcie (port 0); w tym wywołaniu nie ma konfigurowalnego portu preferowanego** [O1][O5]. Adres lokalny (`http://localhost:<port>`) jest używany wewnętrznie, status dla klientów podaje inny adres [O6].
2. Serwer działa tylko wtedy, gdy działa usługa hosta: opublikowany host zdalny (bramka WebRTC dostaje `localApiPort`) albo tryb deweloperski [O6]. Dokumentacja: „Starting the development HTTP API alone does not publish WebRTC" [O7]. Zdalni klienci łączą się przez WebRTC/Signal, nie przez port TCP; serwer self-hosted „publishes no port" [O7][O8]. Dawne publiczne endpointy HTTP i tunel są wycofane (zwracają `host_update_required`) [O7].
3. **Auth**: wszystkie trasy poza sześcioma nieuwierzytelnionymi wymagają `Authorization: Bearer <token sesji>`; brak tokenu to 401 także dla nieznanych tras [O1]. Token pochodzi z `POST /v1/auth/login {username, password}` (hasło członka zespołu, utworzone przy przyjęciu zaproszenia `POST /v1/join {inviteToken, username, password}`) albo `POST /v1/auth/account {accountTicket}` (bilet konta wymieniany w usłudze konta) [O1][O4]. Do tego nagłówki `OpenBot-Protocol-Version` i `OpenBot-App-Version`, negocjowane przez `GET /v1/compatibility`; host musi ogłaszać capability `agent-import-v1` [O1][O2][O7]. Logowanie podlega limitowi prób.
4. Trasy importu: `POST /v1/agent-import/stage` (surowy zip ≤100 MB w ciele; zwraca podgląd z tokenem), `POST /v1/agent-import/apply` (`token`, `keys`, `channelKeys`, `timezone`), `POST /v1/agent-import/discard` (`token`) [O2][O3]. Importować może każdy członek, nie tylko admin; token jest związany z członkiem; skill o nazwie już obecnej w bibliotece hosta jest instalowany bez dodawania rewizji [O3].
5. Linux self-hosted: polecenie `openbot` rozmawia z procesem głównym przez gniazdo Unix (trasy: status, login, name, mobile-connect, logout) — brak trasy importu [O8].
6. Wniosek: na desktopie import odbywa się w aplikacji (Server settings → Import). Z CLI realna ścieżka to `handoff` z zipem. Opcjonalna ścieżka „stage/apply na loopbacku" wymagałaby od użytkownika podania portu i danych logowania członka, a port nie jest odkrywalny [ZAŁ: nie sprawdzałem, czy jakiś plik stanu go zapisuje]. Pewność: wysoka co do faktów z kodu, średnia co do braku innej odkrywalnej ścieżki (nie przejrzałem całego repozytorium).
